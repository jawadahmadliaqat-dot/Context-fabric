# context-fabric — Layer 2 of AmbientOS (Policy Engine)

Turns contextual inputs into validated, cryptographically signed action
permissions. It does **not** build hardware drivers, physical UI, firmware
analysis, or app sandboxing.

- Agent 1 (firmware-liberation-engine) emits `firmware_manifest.json` — hardware facts.
- **Agent 3 (this repo, context-fabric) emits signed `policy_decision.json` — who may do what, in the current context, for a short TTL.**
- Agent 2 (software-trust-layer) reads **both** and runs/traps Wasm apps.
  Note: Agent 2's original brief named the file `policy_token.json`;
  the canonical name unified across the stack is **`policy_decision.json`**
  (Agent 2 should accept both, canonical is `policy_decision.json`).

Stack: Python 3 standard library only. No external dependencies.

## Quick start

```bash
cd Context-fabric   # repo root

# Run the full test suite (10 tests)
python3 -m unittest discover -s tests -v

# Show / update the current context
python3 -m context_fabric.cli context show
python3 -m context_fabric.cli context update \
  --user-present true --user-role GUEST --ambient-state HOME --time-of-day DAY

# Evaluate only (exit 0 = ALLOW, 2 = DENY)
python3 -m context_fabric.cli evaluate --actor-role GUEST --action UnlockDoor --resource SmartLock

# Generate a signed token (DENY is printed, never written as a token file)
python3 -m context_fabric.cli generate \
  --actor-role GUEST --action ToggleLight --resource LivingRoomLights \
  --ttl 60 --out policy_decision.json

# Verify a token (signature + expiry + decision == ALLOW)
python3 -m context_fabric.cli verify --token policy_decision.json
```

## What is in here

| File | Purpose |
|---|---|
| `context_fabric/store.py` | Context State Store (JSON file, validated facts, API + CLI) |
| `context_fabric/evaluator.py` | Declarative policy evaluator (matching semantics only; rules are data) |
| `context_fabric/token.py` | Token generator + `verify_token` (HMAC-SHA256, expiry) |
| `context_fabric/cli.py` | `context` / `evaluate` / `generate` / `verify` commands |
| `policies.json` | All rules, declaratively — edit this, not the code |
| `context.json` | Current context facts (default: GUEST, HOME, DAY, present) |
| `policy_decision.schema.json` | JSON Schema for the ALLOW token |
| `policy_decision.json` | A real sample ALLOW token generated by this code (see below) |
| `dev_signing_key.txt` | **Dev-only** local signing key file (git-ignored, never committed) |
| `tests/test_context_fabric.py` | stdlib `unittest` suite: 5 scenarios + expiry + tamper + store |

## Policies (in `policies.json`, not hardcoded)

- `owner_present_permit_all` — OWNER, when `user_present`, may do all.
- `guest_livingroom_lights_permit` — GUEST may toggle LivingRoom Lights when HOME and present.
- `guest_smartlock_forbid` — GUEST may never `UnlockDoor` on `SmartLock`.
- `guest_heater_forbid` — GUEST may never `ModifyHeater`.
- `unknown_no_sensitive` — UNKNOWN may do nothing sensitive.
- `away_no_unlock_when_absent` — nobody unlocks when `ambient_state=AWAY` and
  `user_present=false`; this Forbid overrides the Owner permit. Owner *present*
  is the exception (the rule's condition then does not match).
- `sleep_guest_heater_forbid` — GUEST heater changes during SLEEP are explicitly forbidden.

Semantics: default DENY; any matching Forbid overrides any Permit; ALLOW
requires at least one matching Permit.

## The 5 test scenarios

| # | Scenario | Expected |
|---|---|---|
| 1 | UNKNOWN / intruder at night, `UnlockDoor` on SmartLock, not present | DENY |
| 2 | GUEST during day at HOME, `ToggleLight` on LivingRoomLights | ALLOW (`livingroom.lights.toggle`) |
| 3 | GUEST tries `UnlockDoor` on SmartLock | DENY (`guest_smartlock_forbid`) |
| 4 | OWNER home & present, `UnlockDoor` on SmartLock | ALLOW (`smartlock.unlock`) |
| 5a | GUEST during SLEEP tries `ModifyHeater` | DENY |
| 5b | `UnlockDoor` while AWAY with `user_present=false` (even OWNER) | DENY (`away_no_unlock_when_absent`) |

Plus: an expired token fails verification, a tampered token fails
verification, and a DENY never carries a `signature`.

## Sample token

`policy_decision.json` in this repo and in `~/workspace/ambient-os/contracts/`
is a real generated ALLOW token: GUEST + `ToggleLight` + `LivingRoomLights`,
capability `livingroom.lights.toggle`, TTL 60s. Because the TTL is
intentionally 60 seconds, it will be **expired by the time you read it** —
that is correct behaviour. Regenerate a fresh one with the `generate`
command above; verification of the sample passed at issuance time.

## Limitation — read this plainly

Signing is **HMAC-SHA256 with a shared dev key** (env var
`CONTEXT_FABRIC_SIGNING_KEY`, or file from `CONTEXT_FABRIC_KEY_FILE`, or the
local (uncommitted) `dev_signing_key.txt` fallback). HMAC is symmetric — anyone with
the key can forge a token. This is a development scheme only, chosen so the
pipeline runs today. Production must move to asymmetric signing (e.g.
Ed25519) with real key management. See `INTERFACE.md` for full details.
